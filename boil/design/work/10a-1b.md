## 1. The return order and the entry frame (4.3, 4.4)

Today `_RETURN_VALUE` reads the result into the C local `temp`. The
operand slot is then cleared (`IR_CONSUME_INPUT`), the frame is unlinked
and `_PyEval_FrameClearAndPop()` runs, and only then does
`IR_STORE_RETURN` store `temp` in the caller. `take_ownership()` can
allocate inside the clear when a frame object exists. A collection there
finds `temp` only in the eval loop's C frame. Today the inline
collection's full scan covers that; after item 5 nothing does.

**The change.**

- `_RETURN_VALUE` stores the result in the caller's destination
  (`_PyFrame_SetReturnValue(dying->previous, temp)`) before it unlinks
  the frame.
- `_YIELD_VALUE` stores in its caller before it unlinks the generator's
  frame. `RETURN_GENERATOR` stores the generator object before
  `_PyThreadState_PopFrame()`.
- The generator return path, where `gen_send_ex2()` reads the entry
  frame's slot, keeps its order. The value is in `entry.stack[0]` until
  `INTERPRETER_EXIT` returns it, and the visitor below covers that slot.

The op signatures lose `res` and `value` as outputs. These are
`(retval --)` and `(--)` forms whose bodies store into the caller. The
`returns` annotation then marks "the body stores in the caller's
return slot", and `IR_STORE_RETURN` after a frame switch is no longer
generated for them.

The other way is to keep the output and store twice. That fails
`_PyFrame_SetReturnValue()`'s debug assertion that a temporary
destination is empty, and it is two forms of one store.

If the compiler's stack-effect metadata (`_PyOpcode_num_pushed`) or the
JIT's abstract interpreter needs `res`, the metadata keeps a pushed count
of 1 through the annotation, not through a stored output. The commit
checks `Lib/test/test_generated_cases.py` and `test_compile`'s stack-depth
tests.

**The entry frame's visitor.** `_PyGC_TraceVisitFrames()` skips frames
owned by the interpreter. It now visits exactly `entry.stack[0]` of each
`FRAME_OWNED_BY_INTERPRETER` frame on the chain: the slot that a
returning frame writes and `INTERPRETER_EXIT` returns. The entry frame's
other fields are poisoned in debug builds and are not read.

**Push before initialize.** `_PyFrame_Initialize()` sets the slots past
the arguments to NULL. No call between a push (`_PyThreadState_PushFrame`,
`_PyFrame_PushUnchecked`) and the initialize of the pushed frame may
collect. The C mode and root_check check this as an adjacency rule:

- in the C mode, a collecting call between the two on a path is an error;
- in root_check, a handler body that pushes and calls a collecting
  function before `_PyFrame_Initialize` is an error.

Today's code passes. Each check has a negative fixture.

**Injection sites** (`_PyGC_INJECT`, 10a-1.md item 8):

- `_PyGC_SITE_INIT_LOCALS`, in `initialize_locals()` after `*args` and
  `**kwargs` are stored;
- `_PyGC_SITE_RETURN`, in `_RETURN_VALUE` between the early store and the
  clear;
- `_PyGC_SITE_TAKE_OWNERSHIP`, in `take_ownership()` before
  `_PyFrame_GetFrameObject()`.

**Tests** (test_gc, 8.4):

- a collection injected inside `initialize_locals` with `*args` and
  `**kwargs`, each checked after the call;
- a collection injected during a return whose frame has a frame object
  (`sys._getframe()` taken), with the result used afterwards. Both
  builds; also under kill on debug.
- the visitor: a C function that calls back into Python. The callback
  returns a fresh object to the entry frame, and the test collects at
  `_PyGC_SITE_RETURN`.

Each test is checked to fail with the change reverted, as far as the
inline full scan allows. The full scan still covers the eval loop's frame
until item 5, so the injected cases fail only after item 5 without
item 1. The commit says which.

## 2. Allocations are safepoints (4.2)

After item 5 an inline collection, run by an allocation past the second
threshold, scans no eval-loop frame. A handler then must not hold an
unanchored object in a C local across an allocation.

- **analyzer.py.** `NON_ESCAPING_FUNCTIONS` splits in two:
  - the calls that cannot collect;
  - `ALLOCATING_FUNCTIONS`, the calls that allocate and run no Python
    code. These include `PyCell_New`, `PyFloat_FromDouble`,
    `PyLong_FromLong`, `PyLong_FromSsize_t`, `PySlice_New`,
    `_PyTuple_FromValues`, `PyUnicode_Concat`, `_PyUnicode_JoinArray`,
    `PyValue_FromDouble`, `PyValue_Object`, `_PyValue_BoxInline`,
    `_PyValue_ObjectRooted`, `_PyValue_BoxInt64` and
    `_PyValue_LshiftInt32`, and the object-returning readers
    `PyTuple_GET_ITEM` and `PyList_GET_ITEM`, which box (question 12).

  Each entry carries a reviewed comment. The comment saying boxing
  "cannot start a collection" is corrected. A property `collecting_calls`
  is the escaping calls plus the allocating ones.
- **root_check.py.** It checks at every collecting call. `ALLOCATING` and
  its exemption are deleted. One new rule: a value loaded from a slot, or
  from a strong traced field of an anchored object, stays anchored across
  an allocating call until that slot or field is written. That is 2.1's
  borrow across a non-reentrant call. Weak fields and caches do not
  qualify. The rule clears the two handlers the rung-0 probe flagged
  (`MAKE_CELL`, `_ALLOCATE_OBJECT`) without code changes. Other flags
  are fixed in bytecodes.c, each by a slot or a span, and listed in the
  record.
- **Stack-passed arguments (question 13) in handlers.** A handler passing
  a C local at position 7 or later to a callee that is not precise must
  anchor it. root_check gains the C mode's rule and its error.
- **ir_generator.py and generators_common.py.** Their `escaping` checks
  become `collecting`:
  - a value without a slot of its own is not live across an allocation;
  - dst takes a result before an allocating call only through a
    temporary;
  - `emit_box_roots` pushes the value root of an inline box across an
    allocating call too.

  The regenerated generated_ir_cases.c.h is the commit's main diff. Its
  instruction cost goes in the record.
- **Tests.** In test_generated_cases:
  - a handler holding a fresh object across `PyLong_FromLong` fails root_check;
  - a slot load held across an allocating call passes;
  - a weak-field load does not pass;
  - a box held across `PyFloat_FromDouble` gets its root pushed.

  The generator's own tests are updated where an expected output changes.

**The work.**

- *Classification, reviewed in the tables.* `_PyObject_Init` and
  `_PyObject_InitVar` are reentrant today through `_PyShape_InitRoot`,
  `_Py_NewReference` and `_PyObject_CheckObjectHeap`. Each gets a reviewed
  entry, or an anchor where it really collects.
  - `_Py_NewReference` calls the reference tracer, a C callback. Whether
    that callback may collect is the question. tracemalloc's allocates
    raw memory only.
  - `__builtin_return_address` is an intrinsic.
- *Known immediates.* `box_*`'s `v` is asserted inline. The C mode treats
  a `PyValue` under `assert(PyValue_IsInline(v))` as holding no object
  from the assertion on. The assertion vanishes in release builds, but
  the fact does not. Tested both ways.
- *Spans.* `gc_alloc`, `_PyObject_GC_New*` and `_PyType_AllocNoTrack` use
  `tp` after the allocation, and question 11 makes the parameter the
  callee's to anchor. Each pushes a span of `tp`. Where the result is
  used after `_PyObject_Init`, the span holds the result too, unless the
  classification shows the init does not collect. This is the one cost on
  the allocation fast path; it is measured (section 5).
- *The clinic wrapper.* `gc_collect` in clinic/gcmodule.c.h is generated.
  Where the C mode rejects the parse ("unexpected 'struct' after
  expression", the `_kwtuple` initializer), the C mode learns that
  construct, the static initializer of a local struct with no object
  fields.

## 4. The eval loop marked

- `Py_GC_PRECISE` goes on `_PyEval_EvalFrameDefault`. The stamp's C mode
  checks its hand-written parts: entry setup, `early_exit`, and the
  `throwflag` path. The `#include "generated_ir_cases.c.h"` line is a
  region the C mode skips by rule, where today it rejects the whole
  function. root_check checks that region, handler by handler.
- **The inline audit is the hard part.** Every function inlined into
  `_PyEval_EvalFrameDefault` must be precise, non-collecting, or clean
  under the C mode (rule 6, 0f). The first audited build lists the
  failures; each is fixed in one of these ways:
  - made to pass;
  - classified with a reviewed entry;
  - `Py_NO_INLINE`, which keeps it opaque and scanned. A helper whose
    only reason to be inlined was speed loses nothing in correctness.

  The list and each disposition go in the record. A helper made
  `Py_NO_INLINE` here is on rung 2's list, to be promoted.
- `_Py_HOT_FUNCTION` and the section attribute: the explicit section
  must win over `.text.hot`. The commit checks `readelf` and that no
  `.cold` part exists (none at d348fd4b198).
- **The tail-call build.** The generator emits `Py_GC_PRECISE` on every
  `TAIL_CALL` handler. This is checked by generating, and by building
  once with clang-21 into `build/tailcall`, configured with
  `--with-tail-call-interp`. If this fork's tail-call build does not
  build at the base, the record says so and the build stays out of the
  gates. It is not one of the gated builds (section 10's "both builds"
  are gcc).

## 6. The trap type and the demonstration (8.3)

6c's header points at a shape whose `type` names the type. A quarantined
block's header gets the root shape of `_PyGC_TrapType`, a static type
whose slots (`tp_repr`, `tp_getattro`, `tp_setattro`, `tp_call`,
`tp_hash`, `tp_richcompare`, `tp_traverse`, `tp_dealloc`, `tp_iter`) abort
with the block's side-table record. In debug builds, `Py_TYPE` aborts on
the trap type: `_Py_TYPE_impl()`'s assertion gains the check. The fill
pattern stays on the rest of the block.

`gc_verify_missed_root` gains:

- `slot_call`: the object's `tp_repr` is called after the collection;
- `store`: the object is stored into a list after the collection, and
  the list is repr'd.

Under kill on debug both abort with the record. test_gc checks the
abort, its message and the record's owner in a child, with
`assert_python_failure`. Retain reports the store as a candidate. Under
ASan all five cases trap.

## Risks

- **Item 2 regenerates every handler that allocates.** The generator may
  reject handlers that keep a slotless value across an allocation, which
  today it allows. Each one needs a slot, a reordering or a box root. The
  count is unknown until the first regeneration, and it is the largest
  unknown in 1b.
- **The inline audit on the eval loop** may list many helpers. `Py_NO_INLINE`
  is the safe answer, and it costs instructions on hot paths.
- **Retention after the clears go**, from stale words in opaque frames that
  rung 2 has not yet promoted, may fail reclamation tests (test_gc's
  `TracingCollectorTests`, test_weakref). The answer is the next
  promotion, named by `gc_live_roots_of()`, not a new clear.
- **Kill on the full suite** has passed only with the eval loop excluded
  by activation range. After item 5, A loses every eval-loop word. A
  trap names a handler or helper that root_check or the C mode missed,
  which is a checker bug, fixed in the checker with a fixture.
