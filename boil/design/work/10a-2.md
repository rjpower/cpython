## 0. The C mode's two gaps

- `--function NAME` exits 0 and prints nothing when the file has no such
  function: `--function method_vectorcall` and `--function no_such_fn`
  look the same. It must fail, naming the function.
- A cast to a typedef the C mode does not know ends the parse: `(PyContext
  *)`, `(PyCFunctionFast)` followed by a call on the next line. Fourteen
  call-layer functions are outside the subset for this alone, as are most
  of descrobject.c's and context.c's. The C mode learns typedef names from
  the file and the headers it already reads, and a test parses a cast to
  a file-local typedef of a function pointer.

The baseline is re-counted after this item, since functions that parse
now report what was hidden.

## 1. The rules the call layer follows

1. **The parameter rule** (question 11). A precise function anchors each
   object parameter it uses after a collecting call. It does so in this
   order of preference:
   a. reorder, so that the parameter is dead at the first collecting call:
      load what it needs from the parameter's immutable strong edges first
      (a builtin's `m_ml` and `m_self`, a bound method's `im_func` and
      `im_self`, a code object's fields), then make the call. Adding an
      edge to the C mode's immutable list needs a line in the list's
      comment saying why it cannot change during a call;
   b. otherwise, the frame's span (rule 2);
   c. `Py_GC_ARGS_ANCHORED`, only for a static function whose callers are
      all precise, which the C mode checks.
2. **The frame's span.** A precise function that needs anchors pushes one
   span per activation, never one per object. Its buffer is a local
   `PyValue` array that holds the parameters that need anchors first,
   then, where the function builds an argument array (`values_of`,
   `_args`, the `*Prepend*` copies), that array in the same buffer. The
   `PY_VECTORCALL_ARGUMENTS_OFFSET` slot is part of the prefix and is
   appended as `PyValue_NULL`: a callee that writes `args[-1]` writes a
   value into a covered slot and restores it, so the span stays valid.
   Values enter only through `_PyValueSpan_Append`. A heap buffer
   (`PyMem_Malloc` past the small size) is the span's base from the
   start; the span is popped before the free on every path, cleanup
   labels included.
3. **The argument array rule.** A callee does not anchor the elements of
   an argument array it receives (`const PyValue *args`): the creator of
   the array does, as the eval loop's frame slots, a frame's span, or an
   opaque caller's scanned frame or followed PyMem block do. A precise
   function that loads an element into a local and holds it across a
   collecting call anchors the local, which the C mode already checks (it
   reports "an element of an array"). The C mode does not prove the
   creator's side for arrays it does not build; kill mode does, since it
   kills what only a precise frame's words held.
4. **Result temporaries** (question 11): a call's result held across a
   later collecting call is an object local. The fix is the frame's span
   or a reorder; the result of the last call is returned, not held.
5. **Object out-parameters go.** `_PyStack_UnpackDict` returns its
   keyword names through a `PyObject **`, whose target escapes. It gets a
   value form whose names tuple is a slot of the frame's span; its four
   callers change with it. `PyObject_CallMethodObjArgs`'s `va_list` walk
   copies the arguments into the frame's span as it reads them.
6. **Statics inlined into precise functions are precise.** The inline
   audit fails on an unchecked static inlined into a precise caller, so
   `check_function_result`, `values_of`, `free_values` and the like are
   marked, and pass the C mode, with their callers. A static that cannot
   pass stays opaque and `Py_NO_INLINE`.

Every rule above is checked by the C mode at build time (the stamp rule)
except rule 3's creator side, which is checked at run time by kill mode.

## 4. Tests

- **Borrowing** (8.4): `_PyGC_TestBorrowAcross(list, callback)`, a core
  function in Python/gc_trace.c marked precise (a shared module is
  extension opaque, so the test function must be in the image), borrows
  `list[0]` into a span, calls `callback`, which clears the list and
  collects, then returns the item's type name. Under plain kill on
  build/debug it returns the name. Its counterpart without the span
  registers itself as a precise test range, as item 7's demonstration
  does, so that the C mode never sees it; under kill it crashes in a
  child, with the crash asserted. The same pair with a weak reference's
  target across a collection injected by `gc_set_stress(1)`. In test_gc.
- **The probe's call-layer cases** (8.1): `test_precise_frames_are_not_roots`
  in test_gc, at 20 runs: the dead object is the argument tuple of a call

  `context.run()`; a value sent into a generator resumed by `next()`.

  lies between two eval-loop frames, and must be freed at the first
  collection. `boil/tools/measure/stale_probe.py` runs the same cases 100

## Risks

- The vectorcall entry points are called through function pointers from
  opaque code, so no vectorcall function can be `Py_GC_ARGS_ANCHORED`;
  the public ones take reorders and spans, and the cost lands on every
  call from C. The measurements attribute it.
- `PY_VECTORCALL_ARGUMENTS_OFFSET`: a callee that writes `args[-1]`
  without restoring it, or writes a non-value there, breaks rule 2; the
  test with a callee that writes it guards the convention.
- Reordering loads before the first collecting call changes the order of
  error checks: a `RecursionError` raised by `cfunction_enter_call` must
  still win over anything the moved loads could raise. They raise
  nothing (field loads); the reorder is limited to field loads.
- typeobject.c's `slot_*` functions are where most of the remaining
  reentrant calls of the call layer are; until 1b they stay opaque and
  scanned, so a stale word there can still keep an object, which the
  probe would show as a failure that 1b owns.
- The C mode's typedef learning may make more functions parse and report
  errors that were hidden; the re-count after item 0 is the baseline the
  burn-down is measured against, not 155.
