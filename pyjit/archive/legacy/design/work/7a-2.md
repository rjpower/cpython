The same-owner S1 dependency uses the same graph as a cross-owner one.
Allocation therefore cannot depend on having several owners. Note 13
section 3.5 withdraws the per-owner shortcut: several earlier calls of
one owner may still be unfinished, so the last earlier call alone is not
a sufficient predecessor. Rung 2a must review the exact graph and storage
bound before code. This is a design obligation, not an implemented fix.

## What rung 1 left, which this rung builds on

- The queue, its phase, `queue_ready`, the pin and the discard counters
  are fields of `struct _gc_runtime_state` (GCState), not of the live
  state. The waiting list, the adopted states and the pending
  sub-processes therefore go there too: the waiting list as
  `queue_wait_head` and `queue_wait_tail` on each interpreter; the
  adopted list and the pending list on the main interpreter's GCState.
  Each is read and written under the head lock.
- The phases stay `QUEUE_INITIALISING`, `QUEUE_OPEN` and
  `QUEUE_CLOSED`. 5.2's freeze is not a phase but a flag in GCState,
  `registration_frozen`, set at the start of the retirement and never
  cleared. The freeze changes only registration: during it the queue
  still accepts and runs calls (step 3 of the close drains what the
  free functions queue). A phase would give the drain two states with
  one meaning. With the flag, each question has one predicate:
  - May the queue drain? `phase == QUEUE_OPEN` (`run_queue_ex()`,
    `live_python_ok()`, unchanged).
  - Do routed calls go to the main interpreter? `phase ==
    QUEUE_CLOSED` (`route_calls()`, unchanged; decision 5).
  - Is a registration refused? A foreign owner, or the owner's
    `registration_frozen`.
  The clear without calls (the never-opened case and the fork child)
  sets the flag too, so a frozen interpreter means the same thing on
  every path.
- `_PyGC_LiveOwner(res, op)` finds the owner among a mark's domain
  (gc_trace.c). 3.4's `_PyGC_LiveOwnerOf(op)` needs the same segment
  lookup against the live interpreters, outside a mark. The lookup
  becomes one static function over a sub-process array, and the two
  callers pass the mark's array or one built under the head lock. It is
  one lookup, not a second form.
- `live_close()` drains only when the current thread belongs to the
  interpreter, and otherwise closes as never opened. That test is
  there for the fork child. Commit 4 replaces it with
  `dispose_after_fork()`, and the close then asserts the thread
  instead (Deletes).
- `_PyGC_Fini()` frees the live state (immortal registry, walk cache)
  after the close. Commit 3 moves that free to deletion: adopted for a
  shared-heap interpreter, freed for an isolated one.
- `get_live()` returns NULL for a closed interpreter, and
  `_PyGC_LiveAddImmortal()` sends a closed interpreter's immortals to
  the main interpreter. After commit 3 the adopted state is reached
  only through the main interpreter's adopted list.
- Tests. Count delivered calls only after collecting until every
  expected object has died (the 9.12 rework): a stale stack word can
  hold one object past a single collection, most often on ASan.
  Stress runs leave out `*test_resize*` and `*WriterTest*` (the writer
  row) and `*test_verify_kill*` until 10a rung 3 lands. Since
  integration 5f74a991472, gate.sh sets `ASAN_OPTIONS` to the line of
  record when the caller has not.

## What changes, by commit

Each commit passes gate 1 on its set on build/default and build/debug,
smallest set first, and is pushed after its gate. The C mode
(`PYTHON_GCVERIFY=kill` on debug) is run on every precise function the
commit edits. Times are budgets from the rung's start; when one is

0. **No unsafe sweep order, and no Python code over a dead set**
   (gc_live.c; about 2 hours; ARCHITECTURE_REVIEW_2.md 5.2 and S3).
   - 5.2, confirmed: `order_dead_first()` returns NULL when its
     allocation fails, and `sweep()` then deallocates in heap order.
     That drops the referrer-first order that
     `Py_TPFLAGS_DEALLOC_READS_REFERENTS` exists for: pyexpat's
     subparser reads its parent parser while it is freed. The fix is
     the rule the order table and the node allocation already follow:
     one failure path. The sweep order is computed before any
     deallocation, and if its allocation fails the pass undoes the dead
     flags and frees nothing. Calls already batched are spliced as
     usual; the next collection retries. Test: a hook that fails the
     ordering allocation once (the `gc_queue_fail_alloc()` pattern,
     returning whether it fired). A flagged chain (the
     `test_dealloc_reads_flagged_referents` fixture) survives the
     failed pass intact, then dies in referrer-first order in the next
     pass, under kill on debug and ASan.
   - S3, to probe first: `debug_write()` can call a Python
     `sys.stderr` writer between the mark and the sweep. A writer that
     releases the GIL lets another interpreter of the domain collect
     while this one holds a dead set; the pin protects interpreter
     storage, not the dead set. Probe: a blocking Python stderr writer,
     `gc.DEBUG_COLLECTABLE`, and a collection from a legacy
     subinterpreter while the writer blocks, under kill and ASan. Fix,
     probed or not, since the rule is cheap: no Python call while a dead
     set is held. Between the mark and the sweep the debug lines go
     into a C buffer in the live state. They are written through
     `sys.stderr` at the drain, where Python may run, or straight to
     the C stderr if the buffer cannot grow (the path that inline
     collections already take). One writer, at one point.
   - Ladder:
     1. The failed-order test.
     2. The S3 probe.
     3. `test_dealloc_reads_referents` and test_gc's `DEBUG_*` tests.
     4. Gate 1 over test_gc, test_pyexpat, test_xml_etree and
        test_finalization.
1. **Order across owners, and completion order within one** (gc_live.c;
   about 4 hours).
   - S1, to probe first: `run_queue_ex()` lets several threads of one
     owner drain at once (the guard is per thread). A referrer's
     finalizer that releases the GIL can be overtaken by its referent's
     finalizer on another thread: FIFO invocation is not completion
     order. Probe: an outer finalizer signals entry and blocks with the
     GIL released while another thread drains, and the test checks that
     the inner finalizer has not run; then a `BufferedWriter` over a
     `FileIO`, both of one owner. The rule below covers this case too,
     so there is one order computation and one wait rule, not one
     within an owner and another across owners.
   - The rule: a call R waits for completion of every earlier
     call P in the batch, of any owner, whose object reaches R's object
     through dead objects. Within one owner this matters only while a
     drain runs on several threads, but the rule is the same. Unrelated
     calls carry no wait and stay parallel; a single-drainer rule would
     bring back the backlog that parallel drains were added to cure. A
     waiting node is popped by no drainer: it sits on its owner's
     waiting list until P's completion releases it to the queue tail.
   - The order table: allocated before `clear_callback_weakrefs()`
     batches the first node, whenever the dead set holds call-bearing
     objects that may depend on one another, even of one owner. Its
     exact storage bound and dependency edges are reviewed in rung 2a;
     the former per-owner bound does not prove the concurrent rule. Its allocation
     failure takes collect()'s one failure path, before any batch
     exists.
   - `order_calls()` between `queue_destroy_hooks()` and `route_calls()`.
     It uses the reviewed graph and accounts for every unfinished
     predecessor; FIFO invocation alone implies no completion edge.
     All dependency storage is reserved before batching begins.
   - A waiting node holds a count of its predecessors and the list of
     nodes that wait on it. The waiting list is visited as a root
     (`_PyGC_LiveVisitRoots()`). When the last predecessor completes,
     on whichever interpreter, the waiting node is spliced to its
     owner's queue tail and that owner's `queue_ready` is set.
   - `gc_queue_info()["waiting"]`.
   - Ladder:
     1. The S1 probe, then its one-owner `BufferedWriter` case.
     2. 9.10, the `BufferedWriter` over a main-owned `FileIO`.
     3. 9.14.
     4. `test_finalizer_order` and `test_dealloc_reads_referents`.
