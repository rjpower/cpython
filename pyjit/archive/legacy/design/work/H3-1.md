## 1. Decision and boundary

The IR word already has a 16-bit handler field. The surrounding machinery
still assumes a byte opcode in several places. Replace those assumptions
with one generated handler domain before adding handlers. This is an
extension of the existing IR, with the same 64-bit word and four 12-bit
fields. It does not change operands, callbacks, root states, event placement
or instruction offsets. It claims no speedup by itself. The current generated domain already has
302 entries: derived operation and NOFB handlers extend beyond 255.

Generate a handler count, IDs, names, classifications and one base map from
the DSL and its derived IR variants. All consumers use that product. IDs
are unsigned 16-bit values; the count has a wider type so 65,536 entries is
representable. Reject an overfull domain during generation. Compiler-only
pseudos live after the handler domain in the compiler's integer namespace;
they are never stored in the low 16 bits of an executable word.

Keep CACHE=0, RESERVED=17 and RESUME=128 for this rung unless a generator
constraint makes a pin impossible. Remove the INSTRUMENTED_LINE=255 pin and
the specialized/instrumented/pseudo boundaries at 256. Allocate ordinary
instructions, derived IR operation variants, specializations, instrumented
instructions and NOFB variants deterministically, preserving existing
ordering within a class where possible. The allocation must not depend on
hand-maintained counts or numeric padding. This layout makes room for
existing families to cross 255 before any new operation is added. Tests
must witness the IDs actually exercised rather than assume that the layout
placed a particular family above that boundary.

`Tools/cases_generator/ir_generator.py` already derives per-NB and NOFB
handlers. Extend it with one explicit domain-building phase after symbolic
DSL analysis. Output generators consume that domain; they must not each
reconstruct its numbering. Remove numeric allocation from
`analyzer.assign_opcodes()` once its callers have moved. Symbolic analysis
and root checking remain independent of numeric assignment. Do not create
a second allocator for ordinary opcodes or a runtime byte-to-wide adapter.
The import/call inventory settles this placement:

- `ir_generator` already imports `analyzer`, `stack` and
  `generators_common`. None imports `ir_generator`; `analyzer` imports the
  symbolic `root_check`/`call_effects` modules, which do not consume IDs.
- `ir_metadata_generator` and `py_metadata_generator` already import
  `ir_generator`. Add the same one-way dependency to `opcode_id_generator`,
  `opcode_metadata_generator` and `uop_id_generator`. Do not make
  `analyzer`, `stack` or `generators_common` import the generator back.
- Each numeric CLI calls `analyze_files()` then `build_handler_domain()`
  once and passes both objects to its output functions. The IR CLI shares
  that product between cases and targets. `generate_ir_from_files()` does
  the same. Numeric generator functions and `test_generated_cases` call
  sites gain an explicit domain parameter; none quietly recomputes it.
- `compute_formats()` and symbolic analysis/root tests remain ID-free.
  Remove `Analysis.opmap/have_arg/min_instrumented` and per-instruction/
  pseudo `.opcode` copies as consumers move; IDs and thresholds derived
  from them belong solely to the domain. `analyzer`'s dump remains symbolic.

Initially move the existing allocation rules into this domain builder
without changing emitted IDs. The final layout described above is a later
commit, after all sinks are ready. The initial domain's index span still
contains the legacy pseudo positions/holes; they are classified as
non-executable throughout and move outside that span at renumbering.

Put the sole generated count in `Include/opcode_ids.h`, also available to
the optional public Py_STATS header. Internal metadata must not become a
public-header dependency. Generate C and Python metadata from the same
model, including metadata/dispatch/pristine/state properties and
compiler-only, specialized, instrumented, operation-variant and NOFB kinds. These are semantic properties,
not tests on ranges of IDs. Event and tool masks remain 8-bit.

## 2. The base map is not the specialization predicate

Extend the existing generated `_PyOpcode_Deopt` to a 16-bit, domain-sized
map and make `_PyIR_BaseOpcode()` its direct accessor. This replaces the
current ordinary-opcode table plus IR shadow lookup. Its meaning preserves
today's behavior:

- A specialization maps to its generic family; a per-NB BINARY_OP variant
  maps to the semantic BINARY_OP family token.
- A NOFB variant maps to the corresponding family token. IR_JUMP maps to
  JUMP_FORWARD.
- Instrumented instructions keep their instrumented identity. Removing
  instrumentation is a separate generated relation; transparent LINE and
  INSTRUCTION wrappers additionally require their per-word displaced state.
- Applying the base map twice gives the same result. Every target is a
  valid metadata entry, although a semantic family token need not have an
  executable dispatch body.

Remove the duplicate IR shadow relation and name-table split when these
consumers move. Generate four separate properties, rather than call all
of them executable validity:

| Property | Meaning |
|---|---|
| Metadata present | This ID has a name/format/family entry; semantic BINARY_OP and compiler pseudos may have metadata without a runtime body. |
| Dispatch body present | A table target exists, including CACHE's deliberate execution trap. This does not establish safe pristine construction. |
| Pristine admissible | A new code object may contain this ID before specialization/monitoring state exists. Ordinary emitted instructions, permitted per-NB/NOFB and inline-constant forms, and CACHE padding have this property. |
| Runtime state required | A bitset names the state needed to install/execute a runtime form, such as displaced line/instruction data or initialized specialization feedback. |

Pristine code rejects runtime monitoring wrappers, stateful
specializations, pseudos and family-only tokens, even when they have
metadata and a dispatch body. `INSTRUMENTED_LINE` illustrates why: a new
code object's `_co_monitoring` is NULL (`Objects/codeobject.c:459`), but
its helper dereferences `monitoring->lines`
(`Python/instrumentation.c:1361`). Runtime installer paths establish each
required-state bit before publishing a replacement ID. Do not infer
admissibility just from family membership or a non-NULL target. Generate
it from the actual compiler-emission forms and their declared state
requirements; audit those producers when generating the table.

Preserve CACHE's existing constructor contract: zeroed two-byte code units
are accepted and padded to whole zero/CACHE words, as
`Lib/test/test_code.py:520` requires for Cython. Executing CACHE still takes
the existing explicit fatal trap (`Python/bytecodes.c:5659`), rather than
being normalized to NOP or newly rejected at construction. RESERVED's
trap is likewise not proof of ordinary construction admissibility.

Move the bounded word/state-admissibility check to the shared
`_PyCode_New()` construction path, carrying forward `check_words()`'s
existing slot/feedback checks and inline-constant replacement semantics.
Remove the public constructor's duplicate call when the shared path owns
its replacement reference. Constructors, `code.replace()`, compiler
assembly, marshal and frozen creation must all reach the same check before
publishing code. This closes marshal's current `_PyCode_Validate()` then
`_PyCode_New()` bypass (`Python/marshal.c:1944`); generic structural
validation is insufficient. Audit each direct `_PyCode_New` caller and
retain ownership/OOM behavior when `check_words` returns a replacement.
This is bounded handler/state validation, not H2's CFG reconstruction,
branch/exception-table proof or new root-map work.

In `specialize.c`, `fb_begin()` currently uses a deopt inequality after
`instr_opcode()` has normalized IR variants. Comparing a raw handler to its
base is **not** an equivalent replacement: generic per-NB and NOFB handlers
also differ from their base. Generate a specialization-kind predicate from
DSL family membership and use it here and in compiler checks. Generate the
instrumentation twin relation from the same model rather than infer it
from the base map or a threshold.

Deoptimization restores the handler from the pristine word, as
`unspecialize()` already does. A base token alone cannot recover the exact
BINARY_OP operation, NOFB layout or displaced wrapper state.
`_PyCode_HandlerFor()` must use generated kind/layout metadata while
preserving those variants and all operand bits. Specializers still run no
Python; H3-1 neither weakens the compiler landing nor establishes the
remaining checker handoffs.

## 4. Displaced opcode storage and publication

Do not widen a packed byte field by casting its address to `uint16_t *`.
Line records have variable delta widths, so such addresses can be unaligned
and an atomic access may cross adjacent state.

Give line monitoring a separately aligned `uint16_t` original-opcode array
indexed by word. Keep its compressed line-delta bytes and their byte-sized
width descriptor. Widen `per_instruction_opcodes` to an aligned 16-bit
array. Allocate using element types and checked sizes, rather than the
current unrelated line-record size. Update ownership, sizing and cleanup
in code objects. Build all replacement state before publishing it; an
allocation failure leaves the previous valid state and propagates, with
one representation and no byte fallback.

Use matching 16-bit accessors for displaced-ID loads and stores. The FT
wrappers in this fork expand to assignments; their spelling alone does not
prove a cross-thread atomic operation. Where a concurrent reader requires
atomic access, use the actual uint16 atomic primitive with the reviewed
ordering. Keep existing lock/world-stop requirements and inspect pointer
publication: initialize before publication and retain its required
release/acquire edge. This proposal does not authorize a new lock-free
publication protocol. Review remote readers, reentrant monitor changes and
disabling callbacks explicitly.

Stored displaced IDs follow the current canonical/event-opcode contract:
`word_opcode()` normalizes through the base map; `_PyCode_HandlerFor()`
uses the pristine word to recover its exact executable variant. Storing a
wider ID must not accidentally change this contract to raw specialized
words. LINE and INSTRUCTION wrappers must restore correctly in either
order, including a high-ID instruction with no feedback entry.

## 5. Serialization, inspection and compatibility

The current remote live reader masks 16 bits (`code_objects.c:372`). Its
binary writer accepts only IDs through MAX_REAL_OPCODE=254, substitutes
OPCODE_NONE for higher values, and writes a byte (`binary_io_writer.c:900,
1172`). Thus some existing per-NB and NOFB samples are already silently
lost; this is required closure, not a hypothetical future issue.

Use a 32-bit opcode field in the binary record and frame deduplication key,
with UINT32_MAX representing None. This admits every 16-bit ID without
reserving a valid handler value as a sentinel. The wire field grows by
three bytes per unique frame. The current C structures already have tail
padding; measure their actual size rather than promise a memory saving.
Bump BINARY_FORMAT_VERSION (currently 1) and update writer, reader, tests
and documentation together. Use one current form; do not add an old-format
fallback within this rung.

The identity must come from the sampled process. Generate immutable
32-byte schema bytes from the IDs, names, base/kind/state and format
metadata, using SHA-256 over one versioned canonical encoding. Encode a
fixed H3-domain schema tag, the word-width/field-layout descriptor and
uint32 count, then records in ID order. Each record has a uint32-length
UTF-8 name, uint16 base and NOFB IDs, uint32 classification/state masks and
the format's flags, four roles, immediate/feedback locations, input count,
destination offset and borrow mask. Use specified little-endian integers
and explicit widths/sign for every scalar; never hash C struct bytes,
padding, timestamps or source paths. Serialize absent entries explicitly.
The encoding version changes if its field set/meaning changes.
Initialize the bytes in the target's debug-offset export alongside its generated
IR schema constant; they do not change during that process's lifetime.
Do not trust a sampler-local hash as proof of target numbering.

Update `_Py_DebugOffsets` and its remote protocol coherently:

1. Give the new layout a distinct eight-byte cookie and fixed bootstrap
   prefix containing cookie, layout-protocol generation and total byte
   size. This protocol version is separate from PY_VERSION_HEX. Export
   the schema bytes in the full table, initialized by
   `_Py_DebugOffsets_INIT`; the existing Python-version/threading fields
   remain explicit fields of the new layout.
2. Update cookie discovery and `_Py_RemoteDebug_ReadDebugOffsets()` in
   `Python/remote_debug.h`. Read only the fixed prefix first; require the
   exact cookie/generation/expected total size before copying the complete
   local `sizeof(_Py_DebugOffsets)`. Reject an older or incompatible layout
   before interpreting its later fields. Do not read a new-size tail from
   an old target and hope Python-version checks detect it afterward.
3. Update the pinned total-size constant/static_assert and field-validation
   lists in `Modules/_remote_debugging/debug_offsets_validation.h:33` with
   the header change; cover new fields and check copied buffers as today.
   `module.c:212-268` validates protocol/layout, Python/threading contracts
   and the **actual target** schema against its local generated schema
   before any handler ID is read or interpreted. A mismatch rejects attach.
   No cross-schema name remapper or old-layout fallback is added.
4. Store the verified target schema in the unwinder/collector's immutable
   capture context and pass it to the binary writer. The writer stamps that
   verified identity, not an unrelated local constant (`writer.c:1241`
   currently stamps local version information). All collector-to-writer
   paths require the context. Make it read-only and constructed by the
   validated unwinder, not caller-provided schema bytes. Local/manual
   frame-writing tests use a distinct local context constructed from the
   local generated constant and cannot claim a foreign target identity.
   File readers compare recorded schema before opcode-name interpretation.

The header/cookie change and every remote discovery/validation consumer
land in the same coherent stage. Existing remote debugging tools must
recognize this protocol generation; the compatibility row below records
that break. Same PY_VERSION_HEX and structural sizes are not sufficient
for attach. A same-version target built with a controlled different schema
must reject before reading its first handler, including when its table is
structurally identical. A mismatched file schema remains a separate test.

The coordinator approved the 32-bit field, UINT32_MAX sentinel and capture
schema identity on 2026-10-29. Section 10 proposes the expanded PROCESS
section 0.2 record for target transport/protocol and codec together; the
implementation documents both. No separate user permission is pending.

Renumbering changes marshalled code contents even though word width stays
64 bits. Bump pyc magic in the first commit that changes emitted IDs, rebuild
frozen code through active targets, and use fresh build prefixes. Do not
remap old IDs. Constructors, code.replace(), unmarshal and freeze must

## 6. Staging and dependencies

The compiler landing is the prerequisite. Coordinate generator, bytecodes
and test-hook ownership with ROOTS and the coordinator before source work.
H3-1 can proceed without H2's new maps because it preserves the existing
operand/root contract and introduces no operation. It must preserve the
no-Python specialization rule, folded operand anchors, in-flight spans,
monitor callbacks and pristine-word deopt. Checker gaps for constructors,
STORE_SUBSCR, stats-only paths and native callees remain the existing ROOTS
handoff. The compiler landing's heap regression is not a missing-reader-root
proof. Allocating buffer-release behavior remains 10a rung 3.

Proposed reviewable commits on a separate branch after this design is
accepted:

1. Establish the generated domain/count/base/kind/state model and explicit
   generator call graph **under existing numbering**. Move the allocator
   without changing emitted executable IDs; verify generated ID equality.
2. Close runtime, constructor/pristine, monitoring, statistics and inspection
   consumers under fixed numbering. Include checked scalar packing/rewriting
   before casts, CACHE preservation and all `_PyCode_New` paths. Add each
   affected test/control with its production change.
3. Close immutable target-schema export, fixed-prefix remote layout protocol,
   verified attach/writer context and the approved 32-bit binary codec with
   its version/schema change. All discovery/reader/writer/collector paths
   change together; no identity is inferred merely from Python version.
4. Only after sink closure, apply the deterministic final allocation, move
   pseudos outside the runtime span and remove threshold exports/usages.
   Bump pyc magic with this emitted-ID change, regenerate all products and
   frozen code, update capture schema and collect fresh final-head gates.

Every gated commit has one coherent representation, with no temporary
runtime option, adapter or fallback. Intermediate gates prove their own
state and cannot be relabeled as final-head evidence. Land the complete
rung after independent review; no new runtime operation precedes it.

H3-2 may add typed float truth only after H3-1's evidence is accepted.
Compare/branch fusion and producer-placement work need the H1/H2
liveness/root contract and measurements. H3-1 does not remove clearing
stores or position publication, change frame passing, add dispatch
special cases or tune adaptive thresholds.

## 7. Proof and negative controls

Every boundary test must record observed handler IDs and word offsets.
A synthetic generator case proves capacity; it does not substitute for
runtime execution of an actual high-ID handler.

Choose real runtime families after allocation and assert their observed
IDs exceed 255. If a needed path remains below it, an isolated coherent
regenerated ID permutation can test that path; retain the exact patch and

production handlers or a runtime test flag just to consume IDs. Counts
65535/65536 and out-of-range scalar inputs need validation before 16-bit
casts. An input of 65536 must not wrap to CACHE, and 65536+NOP must not wrap
