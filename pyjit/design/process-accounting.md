# Process accounting for the R27 stats gate

Status: **partially implemented** (2026-11-06). Stage-one Python launch-audit capture and stage-two finished-process identity landed as runtime `84edb605d31`, paired with the private benchmark consumer. Their merged builds, tests and real-process probes passed; see the [integration receipt](../issues/checkpoint-closure/process-identity-stage2-integration.md). They do not prove exhaustive child coverage. Stage three, a native receipt for each successful child creation, is being implemented against the [concrete schema and lifecycle contract](../issues/checkpoint-closure/process-identity-stage3-proposal.md). Keep the R27 gate red until the complete accounting and boxing requirements pass. Each checkpoint receipt owns its exact source/build identity and full-suite result.

R27 measures boxes in every process of the declared test suite and in all 29 kernels. A dump without a reliable process identity, an uncounted child, an unresolved crash, or an unreadable accounting artifact can hide boxes. Those conditions fail admission. A zero-box result from the processes that happened to dump does not override missing-process evidence. This gate targets the Linux, GIL-enabled stats build; Windows and free-thread profiles have separate status and are not silently counted as covered.

## Identity and evidence files

`Python/pystats.c` creates a unique 40-hex-digit stem per counting interval. `<stem>.run` contains `pid`, `ppid`, tag, and the byte-escaped `/proc/self/cmdline` argv captured when the interval starts. The dump is first written as `<stem>.tmp`, then published as `<stem>.txt`. The stage-two producer patch renames the start marker to `<stem>.done` only after the dump is published. It renames a no-dump, zero-stats interval to `<stem>.zero`; a failed rename leaves visible mismatched evidence. `sys._stats_dump()` followed by more counting obtains another stem. `_Py_StatsAfterFork` creates the child's own marker. The C producer must preserve the marker's original argv; a later argv change or `exec` does not rewrite history.

`Tools/build/check_r27.py` folds a finished `.txt` at most once and retains the parsed dump stem, pid, and tag even when periodic folding deletes the text. Its stage-two reader requires exactly one matching `.done` with the same stem, pid, and tag; it parses and retains the marker's exact filesystem-decoded argv, including surrogateescaped bytes. It rejects an orphan `.done`, missing or malformed identity, a `.run` or `.zero` beside a dump, a duplicate stem, and an unreadable marker. A residual `.run` is an unfinished process; every `.zero` is an explicit no-dump outcome requiring an exact reviewed disposition. The summary reports total and bounded diagnostic samples; raw identity sidecars remain in the evidence directory. An unknown file shape or failed read must not turn into a successful count. `suite_violations` requires complete identity coverage and the existing box-total and owner-accounting checks.

`pyjit/bench/run.py` gives each kernel process its own `-X pystats_dir`, requires one exact `.txt`/`.done` pair and no extra `.run`, `.tmp`, or unrelated artifact, checks the marker pid, parent pid, tag, and argv against the launched command, and journals both raw files before parsing or cleanup. This consumer must land coherently with the stage-two C producer. The full-suite reader can fold many dumps into its summary; the benchmark consumer intentionally requires one process per private directory.

## Launch intent is not child success

`Lib/test/libregrtest/worker.py` records a structured launch-audit event with the recorder pid, event name, executable, exact argv boundaries, explicit environment, classification, and prediction. Shell command strings are opaque; they are never split into purported child argv. An absent or non-exact custom environment cannot be converted by calling arbitrary mapping methods in the audit hook. Relative executable paths and PATH lookup are not resolved against the recorder's cwd; ambiguous Python/shell/env aliases stay unresolved. A failed ledger write sets a sticky worker failure and is reported even if a second error-ledger write also fails. `Tools/build/check_r27.py` rejects truncated, empty, malformed, or unreadable ledgers and retains actual argv and recorder pid.

Audit events are **intent**, not child receipts: the launch can fail, and one `subprocess.Popen` can announce both `Popen` and `posix_spawn`. Predicted counting does not prove a child existed or that it dumped. After stage three, the native receipts are the primary child-coverage evidence; audit records remain diagnostics for options, environment changes, and unresolved shell/exec paths. The gate's admission manifest starts empty. New exceptions require a source-backed process or image disposition, not a broad tag allowlist.

## Stage three: native post-success child receipts

Add one small reporting API in `Include/internal/pycore_pystats.h` and `Python/pystats.c`, such as `_PyStats_ChildCreated(pid_t child, _PyStatsChildSource source, const char *const *exec_candidates, size_t candidate_count)`. The source enum distinguishes `posix_spawn`, `posix_spawnp`, `fork`, `fork1`, `forkpty`, and `_posixsubprocess` fork/exec. Fork sources pass zero candidates; direct spawn passes one; `_posixsubprocess` passes its ordered candidate array. The API is compiled only under `Py_STATS` on Linux and writes a receipt for a successful parent-side `child > 0` once the interpreter has allocated stats. A configured process remains accountable while collection is toggled off; an unmarked child then keeps the gate red. A process that has never allocated stats is outside the measured interval and emits no receipt. It must not call Python, allocate Python objects, or change the Python API's success/error result. It captures the current parent `pid`, the child `pid`, the parent's current interval stem, a process-local monotonic receipt serial, the source enum, and every raw executable candidate in the C marker's byte-escaped format. Include the parent's executable device/inode (from `/proc/self/exe`) so the reader can bind that image to the preflight-verified ELF build ID, rather than trusting a path spelling. If that binding cannot be established, the image is unresolved. The actual child image after an exec remains unknown until independent evidence identifies it. Publish `<parent-stem>.<serial>.child` through a same-directory temporary file and atomic rename; a partial file or publish failure remains evidence of failure, not an accepted absence. A sticky native reporting-error count is printed in the parent's next stats dump. A parent that exits without a dump leaves its `.run` identity and fails the gate. Reset inherited serial/error state in the child after fork, alongside `_Py_StatsAfterFork`.

Insert calls only after the operating system has returned a successful child pid, and before subsequent result construction or warning/error paths can hide it:

| Source | Actual success point | Recorded image information |
| --- | --- | --- |
| `Modules/posixmodule.c:py_posix_spawn` | `err_code == 0`, before `PyValue_FromInt64(pid)` | `posix_spawn` direct path or `posix_spawnp` unresolved PATH target; preserve raw bytes and which operation ran |
| `Modules/posixmodule.c:os_fork_impl`, `os_fork1_impl`, `os_forkpty_impl` | parent `pid > 0`, after releasing fork locks and before warning/result paths | inherited running Python image; a later `exec` is a distinct image transition |
| `Modules/_posixsubprocess.c:fork_exec` | `do_fork_exec` returned `pid > 0`, including its `vfork` branch, before cleanup/result construction | ordered `exec_array` candidates; do not claim which candidate succeeded without later proof |

The fork parent hooks return `void` and may run user callbacks; the receipt call must still be unconditional for `pid > 0` even if a later warning or Python result path fails. Keep the writer outside the child/vfork-unsafe branch. If obtaining a stable parent stem at that location requires a raw snapshot before callbacks, capture only C data without allocating or changing callback order, then publish immediately after fork locks are released. The first implementation must trace these exact control paths and the remaining active `spawnv`/platform launch paths in the chosen Linux build before claiming complete coverage. An `os.exec*` in the same pid is an **image transition**, not child creation; stage one records its intent, while the new image's marker and dump identify the resulting process. A shell or external program can itself start a Python child that bypasses CPython launch hooks; its marker without a native receipt is a gate failure until that process chain has an explicit reviewed account.

The reader adds a strict native-receipt parser and keeps separate `parent_pid`, `child_pid`, parent stem, source, source image/candidate bytes, and publication status. It pairs each receipt with a child `.done`, `.run`, or `.zero` by child pid and marker ppid, then checks the parent interval stem exists and its pid matches. Duplicate receipts for one child pid, reused pids without a disambiguating identity, orphan child markers, unknown native source codes, malformed paths, or a parent sticky reporting error fail closed. A `vfork` child may not create a pre-exec Python marker; if it execs the measured Python image, the new interpreter marker is required. An external image needs a separately reviewed, source-backed disposition: a raw path or prelaunch prediction alone does not prove what executed. Start with every unmatched receipt unresolved and keep the gate red; admit external cases only after validating the actual source path, executable candidate set, and image identity rule. Image classification must never use a broad tag or shell command parse.

## Focused validation before a full suite

The producer and reader are one integration unit. Test a normal stats process, a zero-stats process, `sys._stats_dump()` followed by a second interval, `os.fork` and `subprocess.Popen` children, direct `posix_spawn[p]`, and an external non-Python child. Each true child gets one post-success receipt; a failed spawn gets none. Force a parent-side warning/error after successful fork and verify the receipt persists. Use synthetic receipt/marker fixtures for pid or ppid mismatch, duplicate/reused pid, missing parent stem, malformed or truncated receipt, publication/write failure, unsupported image candidate, and a child marker without a receipt. Test UTF-8 and invalid argv bytes through the C marker and Python reader. Run the benchmark's one-process private-directory probe after the `.txt`/`.done` reader lands, then the coordinator's full stats suite. Do not accept stage three merely because the predicted audit count equals the number of dumps.
