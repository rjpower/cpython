# Register IR v2: pinned handler numbers, and parallel B steps

Status: accepted by the coordinator, 2026-11-04, with the landing time
corrected to 60 minutes. B-pin runs after A5b-4 lands.

Amends [register-ir-v2-packet.md](register-ir-v2-packet.md): finding 9
("dense numbering, no reserved holes"), R2-5, the §4 step table and the
rejected alternative "one magic-number bump for the whole revision". Runtime
paths are relative to the `pyvalue-rc-universal` tree.

Question: the packet runs B2, B4, B5, B6, B7 in sequence because each renumbers
the handlers densely and bumps `PYC_MAGIC_NUMBER`. Why not choose the numbers
ahead of time and merge? Answer: do. The sequence is a property of the
generator, not of the steps.

## 1. Today

A handler number is a position in a sorted list, so any add or remove shifts
every later number.

- **Real opcodes (0 to 255).** `analyzer.py:1237` `assign_opcodes` hard-codes
  CACHE 0, RESERVED 17, RESUME 128, `BINARY_OP_INPLACE_ADD_UNICODE` 3 and
  INSTRUMENTED_LINE 255. It then assigns the no-arg names in sorted order, the
  has-arg names in sorted order (`:1298-1300`), the specialized names from
  RESUME+1 (`:1304`), and the instrumented ones at the top, from
  `256 - len(instrumented)` (`:1309`). `HAVE_ARGUMENT` (41) and
  `MIN_INSTRUMENTED_OPCODE` (233) fall out of the same pass. Removing one
  no-arg name shifts HAVE_ARGUMENT and every has-arg opcode after it.
- **Pseudo-instructions** follow, up to 266.
- **IR-only handlers** (`ir_generator.py:1040` `handler_ids`): from
  `first_ir_only_handler` (`:133`, 267), the `ir_only` names sorted, then the
  `BINARY_OP` operations in `NB_` order, then `<name>_NOFB` in sorted order of
  `nofb_bases` (`:1021`). `num_handlers` (`:4275`) is the end: 302.
  Adding or removing any name moves everything after it.
- **Emitted in.**
  - `Python/ir_targets.h`: the dispatch table (`generate_ir_targets`,
    `ir_generator.py:4280`). It is already hole-safe: `by_index.get(i,
    "UNKNOWN_OPCODE")` (`:4302`).
  - `Include/internal/pycore_ir_metadata.h` (`ir_metadata_generator.py`):
    `IR_FIRST_ONLY_HANDLER` (267), `IR_NUM_HANDLERS` (302), `_PyIR_Formats[302]`
    and `_PyIR_OnlyNames`. The header says a handler without an instruction
    has a zeroed row, without `_PyIR_VALID`.
  - `Lib/_opcode_metadata.py` (`opmap`, `_specialized_opmap`, `_ir_opmap`,
    `HAVE_ARGUMENT`, `MIN_INSTRUMENTED_OPCODE`), `Include/opcode_ids.h`, and
    `pycore_opcode_metadata.h`, all regenerated by `make regen-*`
    (`Makefile.pre.in:2186-2231`).
- **Consumers of a number.** None embeds a literal; all read the generated
  names or tables.
  - `Objects/codeobject.c:797`: validates each unmarshalled word with `handler
    >= IR_NUM_HANDLERS || !(_PyIR_Formats[handler].flags & _PyIR_VALID)`. A
    hole is rejected like any invalid number.
  - `Python/specialize.c:261` and `:306`: order tests against
    `IR_FIRST_ONLY_HANDLER` and `MIN_INSTRUMENTED_OPCODE`. They assume the
    three regions, not density.
  - `Include/internal/pycore_ir.h:276` (`_PyFb_HasEntry`) and `:421`: bound
    checks on `IR_NUM_HANDLERS`.
  - `Lib/opcode.py:23`: `opname = ['<%r>' % op for op in
    range(IR_NUM_HANDLERS)]`, filled from the three maps. Holes print as
    `<n>`, as stock CPython does. `Lib/dis.py` takes names from `opname`.
  - `Modules/_remote_debugging/code_objects.c:495`: reports `word & 0xFFFF`,
    unmasked by any table. The debugger decodes with `dis.opname`, so it
    follows the generated tables.
  - Marshal and `.pyc` store the raw words, so a number is a file-format
    fact. The magic number is `Include/internal/pycore_magic_number.h:332`
    (64404), pinned again by `Lib/test/test_import/__init__.py:3563`.
  - Tests use names. I found no literal handler number in `test_dis.py`,
    `test_ir.py` or `test_external_inspection.py`. Re-check with `rg` at
    B-pin.
  - The JIT front end is not in this tree. B0a/B0b move it to the contract
    table, which is indexed by name through the generated header; confirm that
    B0b adds no literal numbers.

## 2. Pinned numbering

- **The table.** `Tools/cases_generator/ir_numbers.txt`, checked in, one
  `NAME NUMBER` per line, sorted by number. It covers real opcodes, pseudos,
  IR-only handlers, the `BINARY_OP` operations and NOFB forms, plus
  `HAVE_ARGUMENT` and `MIN_INSTRUMENTED_OPCODE`. Section headers are comments
  naming the reserved ranges.
- **Generator rules.** A handler in `bytecodes.c` with no line is an error
  that prints the next free number in its range. A line with no handler is a
  hole, and the line stays as `# removed: NAME NUMBER` so the number is never
  reused. A number outside the opcode class bounds (no-arg below
  HAVE_ARGUMENT, instrumented at or above MIN_INSTRUMENTED_OPCODE) is an error.
  `--check-numbers` runs in CI to prove the table matches the source.
- **Reserved ranges.** One per step, and each step edits only its own lines.
  The counts are the packet's; the ranges leave room for slack.

  | Step | Removes | Adds | Range |
  |---|---|---|---|
  | B2 | 5 dead handlers, `NOT_TAKEN` | 0 | holes in the real-opcode region |
  | B4 | 7 NOFB forms | 1 (`LOAD_ATTR` head) | IR-only: holes at the NOFB tail; one new number |
  | B5 | `PUSH_NULL` | 0 | hole in the real-opcode region |
  | B6 | 0 | 11 fused handlers | IR-only: 16 reserved (11 plus 5 slack) |
  | B7 | 0 | 0 (hidden slots, no handler) | none |

  The IR-only region is `[IR_FIRST_ONLY_HANDLER, IR_NUM_HANDLERS)`. Reserved
  ranges sit after the current end, B4 first, then B6, so `IR_NUM_HANDLERS`
  rises at B-pin, not at each landing. Unused slack stays as holes until
  compaction. Real opcodes are already dense up to the 256 limit, so a removal
  there only frees a number.
- **Compaction (optional, last).** One step after B7 renumbers densely and
  bumps the magic number once. It buys back the holes below and nothing else.
  Skip it unless the measured cost matters.
- **What holes cost.**
  - Dispatch table: 8 bytes per hole in `instruction_funcptr_handler_table`,
    pointing at `UNKNOWN_OPCODE`.
  - `_PyIR_Formats`: one zeroed row per hole. A row has about 20 fields; I
    estimate 64 bytes and have not measured it. About 40 holes (7 + 6 + 16 + 6
    removed slots, less reuse) cost roughly 3 KB of static data in total.
  - `_PyIR_OnlyNames`: 8 bytes per hole.
  - The table must stay below 4,096 entries if B3's 12-bit handler field
    wins G2 (today 302, about 326 after B-pin).
  - Nothing at run time reads a hole. No code assumes density: the
    verifier-style check is the `_PyIR_VALID` flag, `opname` pads holes, and
    the dispatch table already fills them.
  - Holes in the real-opcode region leave no cost beyond a stale name in
    `opname`'s `<n>` slot.

## 3. Magic numbers

One bump per landing on `main`, not per step. Each branch edits no magic line;
the integrator makes the one-line change in `pycore_magic_number.h:328-332`
(plus the comment line and `test_import:3563`) at merge, with the landing's
description. Stale `.pyc` files then never cross a landing, which answers the
rejected alternative: the rule "a bump per format-changing landing" holds, and
the branches stay independent.

What can go wrong:
- Two branches both edit the magic line and conflict. That is the intended
  signal: the later landing resolves by taking the next number.
- A branch tested with a bump it did not choose is fine, because the bump only
  invalidates caches. Run the suite with `PYTHONDONTWRITEBYTECODE=1` or a clean
  `__pycache__`, as with any format branch.
- A landing that changes a number but not the magic loads stale files and
  misexecutes. Guard: B-pin adds a test that hashes `ir_numbers.txt` and the
  format-version comment together, so a table change without a magic change
  fails. This is cheap (about 20 lines) and worth it.
- Two landings between releases of an installed tree leave users with a
  `.pyc` mismatch only if the bump is skipped; this is no new risk.

## 4. Parallel plan

All branches fork from the B-pin commit. Each owns its table lines, so the
generated files differ only in rows each step already owns.

| Step | Shared files it edits | Semantic dependency |
|---|---|---|
| B1 | `regcfg.c`, `ir_generator.py` docstring, `pycore_ir.h` | none |
| B2 | `bytecodes.c`, `codegen.c`, `flowgraph.c`, `instrumentation.c`, `assemble.c` | none |
| B4 | `bytecodes.c`, `specialize.c`, `pycore_feedback.h`, `ir_generator.py` (NOFB, layouts) | none |
| B5 | `bytecodes.c`, `codegen.c`, `flowgraph.c`, `specialize.c` | none |
| B6 | `bytecodes.c`, `flowgraph.c`, `regcfg.c`, `assemble.c` | after B2: its jumps are the conditional jumps without `NOT_TAKEN` |
| B7 | `regcfg.c`, `assemble.c`, `codeobject.c`, `marshal.c` | after B6 only for the hidden-slot count; otherwise none |
| G2 (A4 or B3) | dispatch state, the five `0xFFF` masks, `_remote_debugging` reader | B3 only: after B2 (the packet's rule) |

Real remaining dependencies:
1. **B6 after B2** (semantic). B6 fuses compare-and-jump across the
   fall-through that B2 stops marking with `NOT_TAKEN`. Develop B6 on top of
   the B2 branch, not on the base.
2. **B3 after B2**, if B3 wins G2, for the same reason as today.
3. **Textual overlap, not semantic.** `bytecodes.c`, `flowgraph.c`,
   `codegen.c`, `assemble.c` and `specialize.c` are edited by three to four
   steps each. They are hunks in different instructions; expect small rebases,
   not redesign. The worst pair is B5 and B6 in `flowgraph.c`.
4. **Test churn.** `test_dis` and `test_compile` expectations change in B2, B5,
   B6 and B7. Each branch updates expected output for its own change and
   regenerates after rebase.
5. B1, B4, B7 and G2 (A4) touch disjoint areas and need no ordering.

Landing order: B-pin, then B1, B4, B2, B5, B6, B7, with G2 (A4, or B3 after
B2) wherever its prototype finishes. B4 goes first among the big steps because
it is longest and touches the generator most; B2 before B6 is required; B5
after B2 to keep `flowgraph.c` rebases small.

Estimate, with Sonnet leads and Haiku for mechanical parts (test-expectation
regeneration, `dis` output updates, table lines). The units are the packet's
agent-hours, taken in parallel, plus a rebase unit of 30 minutes per landing.

| Item | Count | Minutes per unit | Wall minutes |
|---|---:|---:|---:|
| B-pin | 1 | 90 | 90 |
| Longest chain, B2 then B6 | 1 | 600 (3 h + 7 h) | 600 |
| Other branches in parallel (B4 9 h, B5 7.5 h, B7 6.5 h, B1 1.5 h) | 4 | within the chain | 0 |
| Landing: rebase, regen, bump, builds, step tests | 5 | 20 | 100 |
| Full suites at the end of the batch | 1 | 40 | 40 |
| Total | | | about 830 (14 h) |

A landing runs the step's tests and a smoke set on both builds, not the full
suites (user ruling, 2026-11-04: a broken bytecode format is not a subtle
failure). The two full suites, 25 to 40 minutes on this host, run once at
the end of the batch and before the measurement. Against the packet's
sequence of 34.5 agent-hours for B1 to B7 plus rebasing each step on the
last, this is about 2.5 times faster in wall-clock, and it costs the same
tokens. Haiku on mechanical parts may cut each branch by 10 to
20 percent; I have not measured that.

## 5. The generator change: B-pin

B-pin lands first, on its own, and changes no behaviour: the table is
generated once from today's numbers, so the output is byte-identical and the
magic number stays 64404.

- `ir_numbers.txt`: about 330 lines, one per handler. Written by a one-off
  script that dumps today's numbers.
- `analyzer.assign_opcodes`: reads the pinned numbers in place of the sorted
  pass (`:1298-1311`); keeps the class-bound checks. About 40 lines changed.
- `ir_generator.handler_ids`, `first_ir_only_handler`, `num_handlers`: read the
  table, and `num_handlers` is `max + 1` of the table including reserved
  ranges. About 40 lines.
- `ir_metadata_generator.py`: emit zeroed rows for holes (already supported)
  and size `_PyIR_OnlyNames` from the table. About 15 lines.
- A `--check-numbers` mode, the CI hook, and the table-hash test of section 3.
  About 60 lines.
- Reserved ranges in `ir_numbers.txt` for B4 and B6: one header comment each,
  with the range bounds. B-pin raises `IR_NUM_HANDLERS` by the reserved slack
  (about 24), which adds the dispatch and `_PyIR_Formats` hole cost above.
  Because that changes table sizes, B-pin is not byte-identical in the
  generated headers; it is behaviour-identical, and bumping the magic number
  is not needed because no valid word changes meaning.

Total: about 160 lines of Python and a data file; 1.5 agent-hours, risk low.
Test: regenerate; the diff shows only the size constants and zero rows; both
suites pass; `--check-numbers` fails on a hand-made unnumbered handler.

## Summary

- Recommendation: add B-pin (a checked-in number table, holes for removals,
  reserved ranges per step) and amend finding 9, R2-5 and the step table so
  steps do not renumber; bump the magic number once per landing at merge.
- Dependencies that remain: B6 after B2 (semantic); B3 after B2 if it wins;
  textual overlap in `bytecodes.c`, `flowgraph.c`, `codegen.c`, `assemble.c`
  and `specialize.c`.
- Landing order: B-pin, B1, B4, B2, B5, B6, B7, with G2 when ready.
- Critical path: B-pin (1.5 h), then B2 and B6 (10 h), then the landings
  with step tests (1.7 h) and one full-suite run (0.7 h): about 14 h
  wall-clock against 34.5 h in sequence.
- Cost of holes: about 24 to 40 table rows and 8 bytes each in the dispatch
  table, roughly 3 KB of static data; nothing assumes density.
