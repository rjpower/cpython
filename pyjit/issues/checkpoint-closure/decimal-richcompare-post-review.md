# Decimal rich comparison: source post-review

Reviewed `decimal-richcompare.diff` against the W5 implementation and `decimal-richcompare-proposal.md`. **No blocking finding for this increment.** The object rich-comparison slot enters through `_Py_VALUE_THUNK_RICHCMP`; the paired value slot returns tagged booleans or `NotImplemented` without projecting them. The Decimal receiver remains a held object, and the current context is resolved before operand conversion. The converter has distinct unsupported and error results. Every converted Decimal owner is released after `mpd_qcmp`; the numerator and denominator attribute values remain owned through exact conversion, including callbacks. The complex-real temporary is closed on conversion success or failure. The FloatOperation and NaN branches preserve the prior W5 status and trap order.

The W5 release build succeeded and the initial comparison/context tests passed (37 tests, including float, complex and Fraction). Terra's added probes confirm that ordering with a FloatOperation trap raises before conversion, equality records the flag without trapping, and reflected int/Decimal comparisons work. A Rational whose numerator getter raises propagates that exception without reading the denominator; a numerator getter that mutates the denominator affects the comparison. This order is present in both project C source blobs `3a440b65695` and `e1229448be3`: each calls `numerator_as_decimal` before `multiply_by_denominator`. Terra's denominator-first control was the pure-Python `decimal` implementation: `build/upstream-release-3a440b6/python` reports the correct source revision but has no `_decimal` extension, and imports `Lib/_pydecimal.py`. That build needs `_decimal` before it can control this C-extension behavior or Decimal performance.

The review covers this source patch and the reported focused probes. Merged debug/release validation and any broader Decimal comparison matrix remain with the coordinator.
