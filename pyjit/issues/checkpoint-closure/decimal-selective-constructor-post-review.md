# Decimal selective constructor: source post-review

Reviewed `decimal-selective-constructor.diff` against the W5 implementation and the approved constructor proposal. **No blocking finding.** The Clinic predicate permits the marker only on a supported `METHOD_NEW` with `@vectorcall`, rejects aliases, deprecated and variadic keyword forms, and keeps it distinct from ordinary selective value methods. Rendering uses copied parameters; cloning creates a new `Function` with a fresh render cache and takes the clone's explicit marker state rather than inheriting it accidentally. The generated object `tp_new` converts the tuple/keyword window at its real compatibility entry and closes the temporary keyword window after the value constructor returns. The generated value vectorcall returns the owned `PyValue` directly. Omitted `value` and explicit `None` remain distinct; the optional context reader borrows its argument for the duration of the constructor call.

The Decimal registration pairs `tp_vectorcall` with `tp_value_vectorcall` after type creation. The generated fast entry asserts its immutable base type; mutable subclasses follow normal type-call behavior. The W5 release probe exercised ordinary constructor defaults, duplicate and unknown keywords, FloatOperation traps, mutable subclass `__new__`/`__init__`, and reassignment of subclass `__new__`. A separate direct `Decimal.__new__(Decimal, ...)` probe passed positional, keyword and duplicate-argument cases. Terra reports 565 Clinic/construction/Context tests passing on the coherent W5 build. These probes cover both entries but do not replace merged integration tests.

One small diagnostic issue remains: a non-core build guard for `@value_constructor` says `@value_function` in its error text. The guard correctly rejects unsupported builds, so this does not affect generated code or checkpoint admission.
