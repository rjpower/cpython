# Full qualification regressions: AST kwargs and dict subclass slot

Observed on the frozen `1ab005e79b8` plus integrated candidate, release binary from `checkpoint-constructor-float-identity-full-v2`. `test_ast` has two failures and `test_opcache.TestSpecializer.test_binary_subscr` one; focused reruns reproduce them, while the same upstream tests pass. This is a diagnosis and review proposal, not a fixture change or an implemented fix.

## Dict/frozendict subclass specialization

`Python/specialize.c` selects `BINARY_OP_SUBSCR_DICT` only when the selected `mp_subscript` is `_PyDict_Subscript`; the bytecode guard independently checks that identity. A `ctypes` `PyType_GetSlot(..., Py_mp_subscript)` probe shows dict and frozendict share the canonical slot on both interpreters, but a simple subclass of either has a different slot in the fork and the canonical slot upstream. A subclass overriding `__getitem__` has a different slot in both. Ordinary lookup results in the test remain correct; lost specialization is real fork behavior, not a stale assertion.

The likely trigger is the new `METH_VALUE | METH_O | METH_COEXIST` `dict_getitem_value` method descriptor: `Objects/typeobject.c:update_one_slot`'s method-descriptor preservation special case requires the existing object slot to equal `d_method->ml_meth`, while the new value method is a distinct function from `_PyDict_Subscript`. The generic slot is installed instead. Confirm the exact branch with a source-level probe/reviewer before implementation.

**Bounded fix option:** expose the exact internal `dict_getitem_value` method provider (or a narrow identity predicate in `dictobject.c`) and, in `update_one_slot` only for the `subscript` row, recognize a `PyMethodDescr_Type` whose declaring type is exactly `dict` or `frozendict`, whose method-definition function is exactly that known value provider and whose target type is a subtype of the descriptor's declaring type. Select the declaring builtin's existing `_PyDict_Subscript` object slot and its paired `tp_value.subscript`; validate the pair before taking it. Do not special-case a mere method name, arbitrary `METH_VALUE` descriptor, unrelated class, overridden `__getitem__`, or a same-name method installed on a mutable intermediate class. Capturing the builtin pair from the descriptor's defining type, rather than the current subtype's possibly stale slot, is necessary for deleting an override and reinheriting the builtin. Preserve multi-slot conflict handling and normal slot update/invalidation.

Compare alternatives with reviewers: a generic descriptor-to-slot-pair mapping could cover future method/provider pairs but needs a real typed identity contract; reverting the value `__getitem__` methods restores slot identity but reintroduces their known call-adapter boxes and is a diagnostic fallback, not closure. Tests: dict/frozendict subclass selected object/value slot identity, initial inheritance, override, override deletion and later mutation, exact/base `__getitem__` methods, missing-key behavior and an overridden getter; existing `test_opcache.test_binary_subscr` and fresh raw attribution. Debug builds must validate the restored pair.

## AST keyword validation and original keyword dictionaries

Focused `test_ast` shows `ASTConstructorTests.test_non_str_kwarg` expects the AST constructor's duplicate-field diagnostic for a non-string key comparing equal to `"id"`; the candidate instead raises `TypeError: keywords must be strings`. `CopyTests.test_replace_non_str_kwarg` likewise expects AST's own unexpected-key diagnostic but gets the same early TypeError. The current release and upstream direct probes agree on this difference. The replace method copies arbitrary kwargs into `payload` and calls `PyObject_Call(type, empty_tuple, payload)` in `Python/Python-ast.c:ast_type_replace`; the AST C initializer itself inspects that dictionary.

`Objects/call.c:_PyValue_Call` passes the original tuple/dict straight to `tp_call` only when `value_call_is_tp_call()` says no value-call slot exists. Pairing `PyType_Type.tp_value.call` changes that decision for ordinary classes. It now expands every nonempty kwargs dict through `_PyValue_StackUnpackDict` → `Python/pyvalue.c:_PyValue_WindowFromDictValues`, which checks that every key is Unicode before the selected `tp_new` or `tp_init` can see the original dictionary. This is a semantic regression at the tuple/dict call boundary, not permission to weaken the general vectorcall string-key rule. The `CALL_FUNCTION_EX` path and the AST replacement C `PyObject_Call` path both reach this conversion; a source-level test should pin both entry routes.

**Preferred contract for review:** add a tuple/dict value-call continuation for the exact selected core `type_call` pair. For a call entering with an already-owned positional tuple and actual kwargs dict, preserve the original dictionary through selected constructor and initializer dispatch; check `type(x)`/type errors and new/init ordering just as `type_call` does, retaining the type, tuple, dict and owned result across callbacks. Use existing value-window providers only where their Unicode-kwnames contract has been satisfied and the conversion itself does not alter required lookup/validation order. A selected C/object-form `tp_new`/`tp_init` must receive the original dict without a preliminary string check; AST's `ast_type_init` is one such consumer. A Python callable or another provider whose original path requires string keys still raises at its original validation point. Do not convert arbitrary non-string dict keys into a nominal vectorcall `kwnames` tuple or remove the global guard.

A narrow semantic-first implementation may route a non-string-key tuple/dict call through the exact legacy object `tp_call` when the actual selected pair is `type_call`, preserving the original dict and its errors. That option is finite and reviewable, but its core object result can still box an inline return on a successful rare path; record that as an explicit remaining core-box debt and do not relabel it as an external boundary or claim constructor closure. Also audit `_Py_slot_tp_new` and `_Py_slot_tp_init` object thunks: their new `_PyValue_StackUnpackDict` step can validate before the former method lookup/callback, even if tuple/dict type-call routing is repaired. Restoring their original object tuple/dict continuation on non-string kwargs, or a dedicated value-aware dictionary contract, must preserve those callbacks and the true object C entry separately.

Validation: both exact AST tests; arbitrary non-string keys for C `METH_VARARGS|METH_KEYWORDS`, AST subclasses and user-defined `__new__`/`__init__`; hash/equality/reentrant effects; descriptor lookup before argument validation; ordinary Python function keyword errors; correct and duplicate Unicode keys; direct `PyObject_Call` from C and Python `CALL_FUNCTION_EX`; result ownership and no silent loss/reordering of dict entries. Run against upstream and both debug/release candidates. Preserve startup-inclusive stats attribution and treat any rare object-return fallback as open rather than masking it.
