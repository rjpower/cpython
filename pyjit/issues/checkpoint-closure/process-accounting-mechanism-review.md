Its regrtest result fails because of the separately diagnosed operator `tp_call` crash, so counts are diagnostic, not admission. ## What the records actually measure

`Python/pystats.c:892` creates a `.run` marker when stats start, including pid, ppid, inherited test tag and `/proc/self/cmdline` arguments; `:1205` replaces it with `.txt` on an ordinary dump. `_Py_StatsAfterFork` creates a child marker after `os.fork`. Thus a leftover marker proves that a counting process began but did not leave a complete dump. It does not by itself prove an intentional kill. One retained marker is a zero-byte file, presumably interrupted before `fclose`; it has no pid/tag/argv and cannot receive an exact admission rule. The operator regression leaves a marker under `test_pyvalue_operator_readers`; fix and recount before classifying that one.

`Lib/test/libregrtest/worker.py:154` records selected audit events before a launch and predicts whether the target will count. In this census, 293 of 423 `counts:false` events lacked `-X pystats` while `-E`/`-I` ignored `PYTHONSTATS`; 130 had the stats environment unset or dropped. Only `subprocess.Popen` and `os.posix_spawn` appear among those 423. They are **events, not unique child processes**: one `python -E -c 'import sys; sys.exit(0)'` launch produced both event types. The raw ledgers also contain 2,879 `subprocess.Popen`, 2,731 `os.posix_spawn` and 22 `os.exec` predicted-true events. `Folded.read_markers` currently discards these predicted-true events, so the summary cannot reconcile a launch to a child marker/dump.

The audit hook has two fail-open capture holes. First, `_launch` uses `shlex` on every argument containing a space, including the payload of a structured `-c` argv. The serialized JSON `argv` is therefore not the actual exec vector, and a future exact rule could conflate different argument boundaries. Second, the hook catches every exception and silently passes; a parse or ledger-write failure can hide a launched build product. For `os.system` and shell-string `Popen`, a shell command is not an exec argv; the hook cannot claim to know its eventual child arguments from `shlex` alone. `_SPAWN_EVENTS` also omits `os.fork`, although forked children are covered by the C run-marker path.

## Minimal instrumentation sequence

1. Preserve the *actual* audit argv list in JSON for structured launch events. Use a separate parse only to recognize a direct build executable or a known `env` prefix. For shell command strings, retain the raw command and mark prediction opaque unless the launched executable is directly known. An opaque launch of a build product must fail the gate pending a reviewed disposition.
2. Replace silent audit-hook failure with a bounded `*.audit-error` ledger (event, parent pid/tag, error class, without leaking arbitrary payloads). Keep the hook non-throwing so test semantics stay intact; make the reader reject every audit-error record. A failure to write this ledger remains a practical observability limit and should be surfaced by a controlled injected-write-failure test, not silently assumed away.
3. Add a separate producer change before attempting finished-process reconciliation. The C dump path removes or renames the finished `.run` marker, and the `.txt` dump does not preserve its pid/ppid/argv; a checker-only change cannot recover that identity. A reviewed sidecar or dump-header record must carry the metadata through successful completion. Only then should the reader retain predicted-true audit events and compare observed child starts. `Popen` and `posix_spawn` can both announce one child, and audit events happen before a launch can fail, so event count alone is not child count.
4. For the common direct launch APIs, consider an explicit **post-success child-pid receipt** at the narrow OS-launch return points (`os.posix_spawn`, `_posixsubprocess.fork_exec`/`Popen`, `os.fork`) rather than trying to infer pid from audit timing. The receipt should identify launch event/child pid and preserve test tag; a failed launch has no receipt. This is a separate reviewed runtime instrumentation packet, not a blanket monkeypatch of `subprocess`. Correlate receipt to completed dump or leftover marker by child pid/ppid; unresolved or duplicate receipts fail. Avoid changing the child argv just to collect stats when the test's purpose is startup flags or environment behavior.
5. Recount after the operator fix. For true intentional kills, admit only exact source-backed command families with a finite maximum and a stated parent assertion/termination reason. Keep zero-byte markers, unknown shell launches, audit errors, unmatched receipts and all uncounted children outside approved shapes failing. No rule has been populated from this census.

This sequence improves coverage without hiding a core box or weakening the static/dynamic PyValue gate. It does not claim that all subprocess boundaries can be counted: tests of ignored or absent environment and fatal termination may need explicit, bounded exceptions after source review.
