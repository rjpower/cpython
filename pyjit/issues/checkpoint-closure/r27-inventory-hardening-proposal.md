# R27 ownership inventory and finite slot-call audit

## Current inventory evidence

The 6aec17ee runtime's `value_ownership.toml` has 146 `[[row]]` entries, 9 `[[manual]]` entries, and no `r27_complete=true` marker. All 143 distinct `Py_VALUE_COMPAT` replacement targets in real API headers are represented by at least one row; the only unmatched spellings are the parameterized `REPLACEMENT` macro in `pyport.h` and the deliberate self-test probe. All 155 listed rows have a callable provider interface in `Include`: 130 direct or inline declarations, and 25 `_PyValue_*` arithmetic names generated by `_PyValue_BINARY_DISPATCHERS` / `_PyValue_INPLACE_DISPATCHERS` in `pycore_value_ops.h`. This is a census of currently *marked* APIs, not proof that every eligible object API has been marked.

Two concrete unmarked string-name siblings remain: `PyObject_GetOptionalAttrString` in `Include/object.h` and `PyMapping_GetOptionalItemString` in `Include/abstract.h`. The former has no string-name value twin; its production uses in `Python/sysmodule.c`, `_csv`, `pyexpat`, `_remote_debugging`, and `Objects/capsule.c` can use `_PyValue_GetOptionalAttr` after creating a Unicode name and preserving the `_PyStatusValue` result. The latter already has a same-signature value twin, `_PyValue_MappingGetOptionalItemString`, declared in `pycore_value_ops.h` and defined in `Objects/abstract.c`; `_sqlite/cursor.c` is one production caller. Add inventory rows using these actual providers, mark the object declarations, and port callers with explicit status and ownership handling. Keep `r27_complete` unset until the wider API survey and these ports are reviewed.

## Minimal static checker hardening

`static_violations()` concatenates `inventory.get('row', []) + inventory.get('manual', [])` without checking their types; a TOML section such as `[row]` instead of `[[row]]` raises `TypeError` and aborts the gate rather than returning an inventory violation. Validate both sections as lists before concatenation, then require each item to be a mapping with C identifier `object` and `value` names. Keep the existing duplicate-object and object-declaration/mark checks.

For each row, require a declared value provider in `Include`: a direct `PyAPI_FUNC(...)`, `Py_LOCAL_INLINE(...)`, `static inline`, or `extern` callable declaration/definition, including a line break before the name. The 25 generated arithmetic providers need a finite exception that verifies the name belongs to the corresponding `X(Name)` dispatcher roster *and* that the declaration-generating macro plus roster invocation still exist. A bare forwarding `#define _PyValue_Add(...)` is insufficient proof; deleting its generated declaration should fail the gate. No other current row needs a macro-only exception. Synthetic negatives: missing direct provider with a correctly marked object declaration; deleted arithmetic roster member with its wrapper macro left intact; malformed `[row]` and `[manual]` section shapes; duplicate object entry. Positive fixtures cover a direct provider and one generated arithmetic provider. These tests change no runtime rule or allowlist.

## Finite indirect slot-call dispositions

The current clang rule intentionally reports a copied slot pointer as a read, so a finite source audit is required. The confirmed outstanding core call-throughs are `_bisectmodule.c`'s two `sq_item` and two `tp_richcompare` loops; `Objects/bytearrayobject.c:1223`'s iterator next; `Modules/mathmodule.c:2424-25`'s paired iterator next; and `Objects/abstract.c:2709`'s aliased `mp_subscript` slice call. `_bisect` also boxes all three value arguments at its entry, so its loop needs a complete value continuation, retaining the same-type direct compare fast path through `_PyValue_CallRichCompare` and fallback order. The bytearray loop is a bounded `_PyValue_IterNext`/owned-item conversion. Math's paired iterator loop needs its own ownership/error-order review. The slice path should use the existing value subscript dispatcher while holding the slice key. The reviewed six-iterator patch removes all six captures in `itertoolsmodule.c` when integrated.

`Objects/listobject.c` stores `tp_richcompare` only to check identity before calling `_PyValue_RichCompareBool`; `Python/specialize.c` compares a slot for specialization; `Objects/call.c`'s three `tp_call` captures are in the public object entry or the explicit tuple/dict call adapter; `Objects/object.c` is the generic comparison adapter. Those are reads or genuine compatibility dispatches, not missed value-native loop calls. No general alias/dataflow checker is justified by this finite list; record each disposition and re-scan after the named ports.
