# Direct object-slot call mapping review

The checker delta distinguishes direct calls through slot members from reads and comparisons, and its fixtures cover direct, parenthesized and cast callees. It intentionally does not prove that a copied slot pointer is never called later. The checkpoint gate therefore needs a finite review of `slot-read` copies and indirect calls before claiming static closure; the fixture for `iternextfunc f = ...; f(it)` demonstrates the gap. Ordinary capability comparisons need not become errors.

The proposed typed-base mappings for dict and long `repr`, dict and long rich comparison, guarded method-descriptor get, exact-Unicode hash, nonnegative sequence item, float conversion, and exact-long shift preserve the relevant dispatch semantics. The ctypes metaclass's base `tp_setattro` and float-to-complex base ternary power have no safe generic substitute and remain unresolved pending typed-base interfaces.

Three itertools mappings need a different design. The direct calls occur inside the object-only `takewhile_next`, `starmap_next`, and `chain_next` implementations. Replacing each with `_PyValue_IterNextThunkExit(_PyValue_IterStep(it))` would turn an inline NEXT result into an object through a THUNK inside core, misclassifying the box and violating R27. These iterators need value-native outer step implementations that propagate `_PyValue_IterStep` status, with object `tp_iternext` wrappers only at the object boundary. `starmap` should reject a non-tuple inline argument without materializing it. Until then, leave the three sites unresolved.
